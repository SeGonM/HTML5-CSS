# 2.2. Especificidad

La especificidad es el mecanismo que usa el navegador para decidir qué regla gana cuando varias reglas distintas apuntan al mismo elemento y establecen la misma propiedad. Es una de las partes más importantes de CSS porque explica por qué un estilo parece ignorarse o por qué una regla de fondo “rompe” a otra sin que tú lo hayas pedido.

En realidad, la especificidad no es un número mágico aislado: es una forma de ordenar las reglas según qué tan concretamente seleccionan al elemento. Cuanto más específico sea el selector, más peso tiene.

## 1. La idea básica

Cuando el navegador resuelve un conflicto, compara:

1. el origen de la regla;
2. si usa `!important`;
3. la especificidad del selector;
4. el orden de aparición.

La especificidad compara solo reglas del mismo origen y, normalmente, dentro de la misma capa. Si dos reglas tienen mismo origen y misma importancia, entonces decide la especificidad. Si siguen empatadas, gana la última que aparece.

Esto significa que una regla muy concreta puede vencer a otra más general, aunque esté escrita antes.

## 2. Cómo se cuenta la especificidad

La forma tradicional es pensar en cuatro columnas:

1. estilos en línea;
2. selectores de ID;
3. clases, atributos y pseudo-clases;
4. elementos y pseudo-elementos.

Se escribe como una especie de “cuatro cifras”:

```css
/* (0, 0, 0, 1) */
button { ... }

/* (0, 0, 1, 0) */
.card { ... }

/* (0, 1, 0, 0) */
#main { ... }
```

La comparación se hace de izquierda a derecha, no como si fuera un número decimal normal.

Por ejemplo:

```css
/* 0-0-1-1 */
article p { color: navy; }

/* 0-1-0-0 */
#contenido { color: teal; }

/* 0-0-2-0 */
.pagina .destacado { color: tomato; }
```

Aquí, `#contenido` gana frente a `article p` porque tiene un ID. Y `.pagina .destacado` gana frente a `article p` porque tiene dos clases.

No importa que `article p` tenga más elementos: la columna del ID o de la clase pesa más.

## 3. Regla práctica: no se compara “como decimal”

Es muy importante entender que esto no es como `0.1 + 0.2 = 0.3`.

La comparación es lexicográfica por columnas:

- primero se mira la columna de ID;
- si empatan, se mira la de clases;
- si empatan, la de tipos;
- si empatan, el orden de aparición resuelve.

Por eso, este selector:

```css
#app .card p
```

tiene más peso que:

```css
.card p
```

aunque el segundo pudiera parecer “más largo” o “más complejo”. No se trata del número total de partes del selector, sino de la potencia de cada pieza.

## 4. Ejemplos con distintas combinaciones

### Selector de tipo

```css
p { color: black; }
```

Tiene especificidad baja porque solo cuenta como elemento.

### Selector de clase

```css
.card { color: red; }
```

La clase aporta más peso que un tipo.

### Selector de ID

```css
#hero { color: blue; }
```

El ID tiene mucha más fuerza que una clase.

### Combinación de varios selectores

```css
section.card p { color: green; }
```

Cuenta como un elemento `section`, una clase `.card` y un elemento `p`:

```text
(0, 1, 2)
```

Eso suele ser más específico que simplemente:

```css
p { color: red; }
```

## 5. Por qué un estilo “no funciona”

Uno de los errores más comunes es escribir una regla que parece correcta, pero otra regla anterior o más específica la reemplaza.

```css
p {
  color: black;
}

.destacado {
  color: red;
}
```

```html
<p class="destacado">Texto</p>
```

Aunque el conjunto de reglas parece sencillo, `.destacado` gana porque su selector es más específico que `p`.

Esto no significa que CSS sea arbitrario: significa que el navegador ha decidido que la regla `.destacado` tiene un peso mayor.

## 6. El caso más común: tres reglas que parecen contradictorias

```css
p {
  color: blue;
}

.container p {
  color: green;
}

#article p {
  color: red;
}
```

```html
<article id="article" class="container">
  <p>Texto</p>
</article>
```

En este caso, el color final será rojo porque `#article p` tiene el selector más específico:

- `p`: (0,0,1)
- `.container p`: (0,1,1)
- `#article p`: (1,0,1)

La diferencia no está en lo “bonito” o “claro” del código, sino en la prioridad calculada por el navegador.

## 7. Qué hacer cuando los estilos se “pelean”

La clave es entender que CSS no se basa en “la última regla que escribiste siempre gana”. La verdadera regla es:

- si una rega es más específica, gana;
- si tienen la misma especificidad, gana la que aparece después;
- si son de origen distinto, gana la prioridad del origen.

Así que cuando algo no funciona, el primer diagnóstico debe ser:

- ¿qué selector tiene más especificidad?
- ¿está escrito sobre otra regla más concreta?
- ¿hay un `!important`?
- ¿es del mismo origen o de otra capa?

## 8. Selectores modernos y su especificidad

### `:is()`

```css
:is(header, main, footer) a {
  color: inherit;
}
```

`:is()` adopta la especificidad de la alternativa más específica dentro de la lista. Es decir, si hay un `header`, `main` o `footer`, el navegador toma la mayor especificidad como referencia.

Esto es útil cuando quieres combinar varios elementos sin hacer un selector enorme y frágil.

### `:where()`

```css
:where(.card) {
  padding: 1rem;
  border: 1px solid #ddd;
}
```

`:where()` siempre tiene especificidad cero. Eso lo hace ideal para estilos base o reset que quieres que sean fáciles de sobrescribir con reglas más concretas.

Por ejemplo:

```css
:where(h1, h2, h3) {
  margin-block: 0.5em 0.25em;
}
```

Esto no “pelea” con otras reglas por peso, porque la especificidad es neutral.

### `:not()`

```css
button:not([disabled]) {
  cursor: pointer;
}
```

`:not()` aporta la especificidad de su argumento. Es decir, `:not([disabled])` cuenta como un atributo, por lo que añade peso. El navegador no ignora esa parte del selector.

Esto tiene un efecto importante: un selector con `:not()` puede ser más específico de lo que parece a primera vista.

## 9. Estilos en línea

Los estilos en línea tienen la máxima prioridad de especificidad:

```html
<p style="color: red;">Texto</p>
```

Esto suele ganar sobre casi cualquier regla de CSS normal, salvo `!important` en una hoja de estilo del autor.

```css
p {
  color: blue !important;
}
```

En este caso, la regla con `!important` gana sobre el estilo inline, porque la prioridad del origen y la marca de importancia pueden sobreponerse.

Aunque los estilos inline no suelen ser recomendados en proyectos grandes, son un punto importante para entender cómo el navegador decide.

## 10. `!important`: herramienta de excepción, no de rutina

```css
.card {
  color: black;
}

.card {
  color: green !important;
}
```

La regla con `!important` gana, incluso si está más arriba o si la otra es más específica.

Sin embargo, esto trae consecuencias:

- hace que el CSS sea más difícil de depurar;
- complica la reutilización de estilos;
- puede romper la lógica de capas y componentes;
- genera reglas que parecen “mágicas”.

La recomendación general es:

- evitar `!important` en la mayoría de casos;
- usarlo solo en casos muy concretos, como una utilidad de accesibilidad o una regla que debe imponerse por razones funcionales.

## 11. Las capas (`@layer`) y la especificidad

CSS Layers permiten organizar reglas por prioridad de forma explícita. Esto evita que el orden del archivo domine todo.

```css
@layer reset, base, components, utilities;

@layer base {
  :where(h1, h2, h3) {
    line-height: 1.1;
  }
}

@layer components {
  .card {
    padding: 1rem;
  }
}
```

La idea es que las capas tienen prioridad por orden, y el navegador resuelve primero la capa antes de mirar la especificidad.

Esto significa que, en muchos proyectos, una capa de componentes puede sobrescribir una capa base aunque el selector sea menos específico, porque la capa es más prioritaria. No obstante, si dos reglas están en la misma capa, entonces sí se usa la especificidad y el orden de aparición.

### Cuándo son útiles

- cuando quieres un reset ligero;
- cuando un framework debe imponerse sobre tus estilos base;
- cuando quieres controlar la prioridad sin abusar de `!important`;
- cuando necesitas más claridad en proyectos grandes.

## 12. La lógica completa de la cascada

Cuando el navegador calcula el valor final de una propiedad, normalmente hace lo siguiente:

1. prueba qué reglas aplican al elemento;
2. descarta las que no coinciden;
3. ordena por origen;
4. aplica `!important` y prioridad por fuente;
5. compara especificidad;
6. si sigue en empate, usa el último en aparecer.

Por eso, escribir CSS no es solo “poner reglas al azar”. Hay un algoritmo detrás, y tu trabajo es hacerlo predecible.

## 13. Ejemplo de conflicto real en un componente

```css
.card {
  background: white;
  padding: 1rem;
}

.theme-dark .card {
  background: #111827;
}

.card.featured {
  background: gold;
}
```

```html
<div class="theme-dark">
  <article class="card featured">Contenido</article>
</div>
```

¿Qué gana? La última regla, porque el selector `.card.featured` es más específico que `.theme-dark .card` y `.card`.

La regla es:

- `.card`: (0,1,0)
- `.theme-dark .card`: (0,2,0)
- `.card.featured`: (0,2,0) pero con más elementos de clase y más concreta

Si una de esas reglas estuviera en una capa distinta, podría ganar por la capa antes que por especificidad.

## 14. Una regla útil para escribir CSS limpio

No intentes “ganar siempre” con más especificidad. Eso conduce a CSS frágil. Un buen CSS suele seguir esta idea:

- usar clases para componentes;
- evitar depender de etiquetas generales (`div p`, `section ul li`);
- no escribir selectores absurdamente largos;
- no abusar de `!important`;
- mantener una arquitectura de capas y componentes clara.

Es más fácil mantener esto:

```css
.card__title { font-weight: 700; }
```

Que esto:

```css
main > section:nth-child(2) .wrapper .content h2.title { ... }
```

El segundo selector puede funcionar, pero genera dependencias muy frágiles.

## 15. Cómo detectar el conflicto correcto

Cuando algo no se aplica:

- abre la inspección del navegador;
- revisa las reglas que le afectan al elemento;
- mira si hay otra regla con mayor peso;
- comprueba si existe un `!important` o una capa superior;
- compara la especificidad visualmente en el panel de estilos.

Esto es una de las habilidades más valiosas para un desarrollador de front-end, porque te permite arreglar problemas sin improvisar soluciones peligrosas.

## 16. Resumen mental rápido

Puedes recordar la idea así:

- selector = qué elementos toca;
- especificidad = cuán concreto es ese selector;
- origen = de dónde viene la regla;
- `!important` = prioridad máxima dentro del origen;
- orden = desempate final si todo lo demás coincide.

La regla final es:

> El navegador no decide “a ojo”; decide por prioridad calculada y predecible.

## 17. En conclusión

La especificidad es la herramienta que mantiene el CSS ordenado y controlado. Sin ella, todas las reglas competirían sin criterio y el navegador no podría decidir cuál debe aplicar. Pero como cualquier mecanismo poderoso, debe usarse con criterio.

Dominar la especificidad te ayuda a:

- entender por qué una regla gana y otra pierde;
- escribir CSS más protegido frente a cambios accidentales;
- evitar la dependencia de `!important`;
- crear sistemas más escalables y menos frágiles.

La especificidad es una de las bases más importantes para “leer” CSS como un lenguaje lógico y no como un conjunto de reglas que “a veces funcionan”.
